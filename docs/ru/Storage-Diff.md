Изменения хранилищ (`<diff>`)
==============================

[English version](../en/Storage-Diff.md)

`<diff>` — это ожидание теста: что должно измениться в хранилище после выполнения кода
приложения. Блок одинаково работает для всех хранилищ фреймворка — PostgreSQL, Redis, Kafka и ваших
собственных, — поэтому общие правила собраны здесь, а особенности конкретного модуля описаны в его
документации.

## Когда нужен diff

Тест, который пишет в базу, кэш или очередь, обычно проверяет две вещи: ответ метода (`<response>`)
и состояние хранилища. Для второго и используется `<diff>`:

```xml
<diff storage="dataSource">
    <insert key="users/100">
        <id type="Long">100</id>
        <name>Ivan</name>
    </insert>
    <update key="orders/42">
        <status>PAID</status>
    </update>
    <delete key="orders/43"/>
</diff>
```

`storage` — имя хранилища; для подключений модуля оно совпадает с именем подключения. Одно
хранилище — один блок `<diff>`; если изменилось несколько хранилищ, блоков будет несколько. Внутри —
записи: строки таблиц, ключи Redis, элементы вашей коллекции.

## Как читать diff

### Состояние до и после

Для snapshot-хранилищ фреймворк запоминает содержимое перед частью теста и после неё. Delta-хранилища
(например, PostgreSQL с журналом изменений) сами сообщают, что изменилось. В обоих случаях в файл
попадает только разница; если изменений нет, блока быть не должно.

Diff считается от последнего зафиксированного состояния: внутри кейса каждая часть сравнивается
с состоянием после предыдущей части, а между кейсами — с состоянием, которое оставил предыдущий
кейс (если модуль не очищает хранилище сам). Поэтому кейс, который оставляет данные, влияет на
ожидание следующего кейса.

### Операции

* `insert` — запись появилась; тело содержит значение целиком;
* `update` — запись существует и изменилась; тело содержит только изменения, атрибуты — полные
  метаданные значения после теста;
* `delete` — запись или поле исчезло; тела нет, только `key`.

Тег операции у записи обязателен: у корня хранилища нет вышестоящей операции. Даже если ключ
`orders` — валидный XML-тег, запись пишется `<update key="orders">`, а не `<orders>`.

Для последовательностей (`List`, массив, `Deque`) тело `update` — снапшот нового состояния, а не
набор изменений: у элементов нет собственного `key`. `Set` пишется добавленными и удалёнными
элементами.

### Ключ, тип и атрибуты

Ключ записи пишется строкой (атрибут `key`), если тело ключа скалярное, и объектом (элемент `<key>`),
если структурное. Форму определяет тело, которое вернул презентер ключа, а не объявленный Java-тип;
для незарегистрированного типа скалярный ключ пишется строкой, структурный — объектом.

Атрибуты — обычная map «имя → значение». Они описывают значение после теста, а не изменение:
`insert` и `update` пишут все атрибуты элемента, поэтому неизменившийся `ttl` повторяется.
Отсутствие атрибута означает, что у значения его нет; что элемент потерял, видно по предыдущему
состоянию того же ключа. `type` — не обычный атрибут, а метка формы: она пишется, когда по телу
нельзя однозначно восстановить форму значения.

Для текстового ключа порядок такой: сначала `key`, затем `type`, затем остальные атрибуты. У
объектного ключа `type` и атрибуты стоят на самом элементе, а `<key>` — дочерний элемент.

### Вложенность и наследование операции

Операция наследуется от ближайшего вышестоящего тега операции. Поэтому внутри `<update>`
изменившееся поле пишется своим именем, добавившееся — `insert key="..."`, исчезнувшее —
`delete key="..."`. Внутри `<insert>` и `<delete>` тело — снапшот: поля пишутся именами, потому
что операция унаследована. Тег операции повторяется только тогда, когда операция отличается от
унаследованной или имя нельзя использовать как XML-тег.

Правила применяются рекурсивно: значения мап — по ключам, поля объектов — по полям, элементы
коллекций — по элементам. Поэтому в diff видно только то, что действительно изменилось, на любой
глубине:

```xml
<update key="users/100">
    <profile>
        <city>Moscow</city>
    </profile>
</update>
```

Исключение — элемент коллекции или значение повторяющегося поля `MultiValueMap`: у них нет
отдельного `key`, поэтому `delete` несёт удалённое значение, иначе его не идентифицировать:

```xml
<delete key="header">b</delete>
```

Тело `insert` и `delete` — это просто данные: поля и элементы коллекций пишутся своими именами.
Маркер операции нужен только полю с не-теговым именем, и это унаследованная операция:
`<insert key="...">` внутри `insert`, `<update key="...">` внутри `update`,
`<delete key="...">` внутри `delete`.

```xml
<update key="orders/42">
    <status>PAID</status>
    <insert key="paidAt" type="Instant">2026-01-01T10:00:00Z</insert>
</update>
```

Ограничение формата: пустое значение с атрибутами (например, пустая строка с `ttl`) пишется
самозакрывающимся элементом и неотличимо от значения без тела.

### Порядок полей и элементов

Порядок в файле не нужно поддерживать руками: при одинаковых данных он всегда одинаковый.

* Поля объекта идут в порядке объявления (`@JsonPropertyOrder` его меняет); у строки таблицы —
  в порядке колонок.
* Коллекции и мапы, у которых есть собственный порядок (список, `LinkedHashSet`, `SortedSet`,
  `EnumSet`, `Deque`, отсортированная мапа, `EnumMap`), идут так, как лежат в источнике.
* Неупорядоченная мапа (`HashMap`) сортируется по записанному ключу; `HashSet` — по записанному
  элементу.
* `TreeMap`/`TreeSet` считаются упорядоченными; если их компаратор опирается на identity hash,
  порядок не будет стабильным — используйте `LinkedHashMap`/`LinkedHashSet` или свой рендерер.
* Порядок записей (строк таблиц, ключей Redis) задаёт карта снапшота: `LinkedHashMap`/`SortedMap`
  сохраняют свой порядок, `HashMap` сортируется по записанному ключу.
* Атрибуты значения (`ttl`, `score`) — обычная map: `LinkedHashMap`/`SortedMap` сохраняют свой
  порядок, `HashMap` и `Map.of` с 2+ атрибутами сортируются по имени. `type` идёт первым среди
  метаданных, но после `key`.

Если порядок в эталоне всё же оказался другим, это повод перегенерировать diff, а не править его
вручную.

### Что не попадает в diff

* данные, исключённые настройками (`ignore`, `excludedFields`);
* изменения, которые хранилище не показало фреймворку (например, PostgreSQL при отключённых
  триггерах);
* смена класса непустой мапы: она сравнивается по содержимому и не пишет тип;
* служебные данные самого модуля.

### Как обновить ожидания

Diff не пишут руками — его генерируют из фактического состояния:

* `-Dintegration.testing.assertion=SaveActualData` — прогон записывает фактические данные в файл
  теста;
* режим `file` в [плагине IntelliJ IDEA](IDEA-Plugin.md) — сравнение в обычном diff-диалоге и
  кнопка сохранения результата.

## Как настроить

Операции и общая форма diff фиксированы: записи всегда пишутся тегами `insert`, `update` и
`delete`. Старая секция `integration.testing.storage` больше не нужна — её можно удалить из
`application-test.yml`.

Остальное настраивается в модулях:

| Что настраивается                                                                            | Модуль     | Где описано                                 |
|----------------------------------------------------------------------------------------------|------------|---------------------------------------------|
| Подключения, `defaultSchema`, `columns` (`ignore`, `excludedFields`), `sequenceRestartValue` | PostgreSQL | [Конфигурация](postgresql/Configuration.md) |
| Схемы сериализации, `ignore` по маскам ключей, `multipleDatabases`, `excludedFields`         | Redis      | [Конфигурация](redis/Configuration.md)      |
| `ignore`, `ignore-inbound`, `excluded-fields`                                                | Kafka      | [Конфигурация](kafka/Configuration.md)      |

Формат ключей записей тоже зависит от модуля: у PostgreSQL это `[schema.]table/pk`, у Redis —
`key` или `db/key` при `multipleDatabases`. Пример diff по произвольному хранилищу — в разделе
[Записи и заголовки](kafka/Records-and-Headers.md).

## Свои типы

Если стандартных правил не хватает, зарегистрируйте презентер или рендерер через `TestSetupModule`:

| Метод                                                           | Что задаёт                                                   |
|-----------------------------------------------------------------|--------------------------------------------------------------|
| `addDiffKeyPresenter(Class<T>, DiffPresenter<? super T>)`       | представление ключа записи                                   |
| `addDiffPresenter(Class<T>, DiffPresenter<? super T>)`          | представление значения: тело, тип и атрибуты                 |
| `addDiffRenderer(Class<T>, DiffRenderer<? extends T>)`          | рендерер тела: как считается и записывается разница тела     |
| `addEqualsForType(Class<T>, BiPredicate<? super T, ? super T>)` | предикат равенства: изменение такого типа не попадает в diff |

Подробные контракты, примеры и правила — в разделе
[Расширение diff](Storage-Diff-Extensibility.md). Для кастомных структур Redis достаточно описать
чтение и запись значения — см. [Расширяемость Redis](redis/Extensibility.md).
