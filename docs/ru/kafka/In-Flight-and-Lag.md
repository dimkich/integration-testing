In-Flight трекинг и контроль лага
=================================

[English version](../../en/kafka/In-Flight-and-Lag.md)

Зачем это нужно
---------------

Работа с Kafka асинхронна: приложение может получить сообщение, но ещё не завершить его обработку,
или отправить ответ, который брокеру ещё предстоит раздать потребителям. Если завершить кейс сразу,
тест начнёт сравнивать результаты слишком рано и будет «мигать».

Поэтому перед проверкой `<outboundMessage>` фреймворк ждёт, пока все сообщения будут действительно
обработаны, а уже потом сверяет результаты. Есть два режима этого ожидания.

Что выбрать
-----------

Ничего настраивать не нужно: по умолчанию работает `inflight = true`, и этого достаточно почти
всегда. Переключитесь на `@EnableTestKafka(inflight = false)`, если:

* SUT запущен в отдельном процессе или Docker-контейнере — клиенты приложения не видны из JVM теста;
* тест зависает, потому что группа потребителей приложения не видна фреймворку.

Режим `inflight = true` (по умолчанию)
--------------------------------------

При `@EnableTestKafka` без параметров фреймворк сам отслеживает, что приложение отправляет и читает:

* сколько сообщений отправлено и каким из них брокер уже подтвердил приём;
* какие offset'ы закоммитили потребители приложения;
* на какие топики и партиции подписаны потребители (включая подписку по маске и ручной assign);
* транзакционные отправки: сообщения внутри транзакции учитываются только после её commit.

Пока остаётся хотя бы одно необработанное сообщение, лаг считается ненулевым и фреймворк ждёт.

Ограничения режима:

* он действует только на тесты с `@EnableTestKafka(inflight = true)`;
* потребитель без `group.id` не может быть сопоставлен с группой и не учитывается;
* при откате транзакции (abort) её сообщения не учитываются — так же, как их не увидит и обычный
  потребитель с `read_committed`;
* режим видит только клиентов приложения в этой же JVM: группа из внешнего процесса не видна, для
  неё используйте `inflight = false`.

Режим `inflight = false` (Admin API)
------------------------------------

```java

@EnableTestKafka(inflight = false)
class LagMonitoringTest {
}
```

Фреймворк не следит за клиентами приложения, а спрашивает брокер о состоянии групп потребителей:
сравнивает размер журнала (end offset) с закоммиченными offset'ами. Лаг есть, пока хотя бы одна
активная группа не дочитала сообщения.

Особенности:

* группы в состояниях EMPTY/DEAD не учитываются;
* если офсет группы ещё неизвестен (только что созданный топик), он считается нулевым — лаг будет
  держаться, пока сообщение не будет прочитано;
* открытые транзакции не видны, поэтому этот режим менее точен для транзакционных сценариев.

Основной режим — `inflight = true`: он быстрее, потому что лаг и готовность групп определяются по
состоянию клиентов приложения, без обращений к брокеру. Режим Admin API используйте только тогда,
когда клиенты приложения недоступны (или SUT работает во внешнем процессе): каждая проверка лага —
это несколько запросов к брокеру, поэтому ожидание медленнее. В тестах модуля режим Admin API
используется как «второе мнение»: один и тот же сценарий прогоняется в обоих режимах.

Как фреймворк ждёт завершения
-----------------------------

1. **Отправка приложения.** `@EnableTestKafka` ждёт, пока завершатся отправки, сделанные приложением
   в рамках кейса.
2. **Готовность.** Ожидание завершения выполняется после инициализации теста, поэтому SUT-листенеры,
   запускаемые инициализацией, успевают подняться. Сначала фреймворк ждёт до
   `startup-stabilization-timeout-seconds` (по умолчанию 30 секунд), пока сниффер получит назначение,
   а группы из `expected-groups` появятся и получат партиции; при заданных группах все известные
   группы должны ещё и перестать перестраиваться. Если готовность не достигнута к концу таймаута,
   тест падает с сообщением `Kafka wait completion timeout. expected consumer groups are not ready:
   ...` (см. [Конфигурацию](Configuration.md)).
3. **Цикл проверок.** Готовность перепроверяется каждые `lag-polling-interval-ms` (по умолчанию 5 мс),
   но не чаще, чем раз в `readiness-polling-interval-ms`. После достижения готовности проверяется лаг,
   пока он не исчезнет или не истечёт `lag-polling-timeout-ms` (по умолчанию 10 секунд).
4. **Результат.** Как только лаг исчез и все потребители готовы, кейс продолжается. Если время вышло,
   кейс падает с ошибкой:

```text
Kafka wait completion timeout. Unprocessed messages remaining on broker.
```

Если причина — неготовность сниффера или ожидаемых групп, сообщение будет другим, например
`Kafka wait completion timeout. expected consumer groups are not ready: ...`.

Если такая ошибка повторяется, увеличьте `lag-polling-timeout-ms` — например, приложение обрабатывает
сообщения батчами или обращается к внешнему сервису.

Если приложение сознательно оставляет упавшее сообщение незакоммиченным (rollback, ручной ack,
пропущенная «ядовитая» запись), увеличение таймаута не поможет: лаг не исчезнет сам. В этом случае
используйте [Сценарии с ошибками и незакоммиченными offset'ами](Error-Handling.md).

Чтение топиков сниффером
------------------------

* сниффер читает все топики, кроме внутренних (их имена начинаются с `__`);
* при первом подключении старая история топика пропускается — читаются только новые сообщения;
* топик, созданный во время теста, читается с самого начала — поэтому сценарий «Cold Start» работает
  без специальной настройки;
* подписка по маске (`topics` с регулярным выражением) поддерживается так же, как точные топики;
* если приложение само назначает партиции (`assign`) вместо подписки, это тоже отслеживается.

Настройка таймаутов
-------------------

```yaml
integration:
  testing:
    kafka:
      # пауза между проверками лага
      lag-polling-interval-ms: 5
      # сколько всего ждать исчезновения лага
      lag-polling-timeout-ms: 10000
      # пауза между проверками готовности ожидаемых групп
      readiness-polling-interval-ms: 100
      # ожидание готовности SUT перед проверкой лага
      startup-stabilization-timeout-seconds: 30
```

Сравнение режимов
-----------------

|                                   | `inflight = true` (по умолчанию)        | `inflight = false`                                                                 |
|-----------------------------------|-----------------------------------------|------------------------------------------------------------------------------------|
| Как определяется лаг              | по клиентам приложения                  | через Admin API брокера                                                            |
| Как определяется готовность групп | по состоянию клиентов приложения        | через Admin API                                                                    |
| Транзакции                        | учитываются точно (только после commit) | не видны                                                                           |
| SUT в другой JVM                  | не поддерживается                       | поддерживается                                                                     |
| Скорость проверок                 | высокая                                 | ниже: запросы к брокеру на каждой проверке                                         |
| Когда выбирать                    | основной режим                          | только если клиенты приложения недоступны (или нужно проверить сценарий «снаружи») |

В каких сценариях это проверяется
---------------------------------

| Сценарий         | Что проверяет                                                          |
|------------------|------------------------------------------------------------------------|
| Slow SUT         | приложение отвечает с задержкой — тест не завершается раньше времени   |
| Cold Start       | топик создан в середине теста — начальные сообщения не теряются        |
| Pattern Matching | подписка приложения по маске — ответы собираются                       |
| Transactions     | commit/abort и отправка offset'ов — лаг учитывает только закоммиченное |
| Assign           | ручное назначение партиций — сообщения всё равно отслеживаются         |
