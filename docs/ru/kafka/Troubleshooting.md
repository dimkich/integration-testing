Решение проблем и частые ошибки в тестах Kafka
===============================================

[English version](../../en/kafka/Troubleshooting.md)

Ошибка: `Kafka wait completion timeout. Unprocessed messages remaining on broker.`
----------------------------------------------------------------------------------

### Симптомы

Кейс падает с сообщением `Kafka wait completion timeout. Unprocessed messages remaining on broker.`
Обычно ошибка появляется, когда приложение не успевает обработать сообщения.

### Причина 1: приложению нужно больше времени

Приложение обрабатывает сообщения батчами, ходит во внешний сервис или отвечает с задержкой.

**Решение:** увеличьте `lag-polling-timeout-ms` (по умолчанию 10000 мс):

```yaml
integration:
  testing:
    kafka:
      lag-polling-timeout-ms: 20000
```

### Причина 2: потребитель не коммитит offset'ы

Приложение читает сообщения, но не подтверждает их (например, отключён auto-commit, а ручной коммит
не настроен), либо сознательно пропускает упавшую запись без коммита её offset'а. Тогда для
фреймворка сообщения остаются необработанными.

**Решение:** заставьте приложение закоммитить offset пропущенной записи (например,
`DefaultErrorHandler.setCommitRecovered(true)`) или принудительно закоммитьте его из теста через
хук на метод. Оба варианта описаны в разделе
[Сценарии с ошибками и незакоммиченными offset'ами](Error-Handling.md).

### Причина 3: сообщение осталось в открытой транзакции

Приложение отправило сообщение в транзакции, но не закоммитило её. В режиме по умолчанию такие
сообщения намеренно не считаются обработанными.

**Решение:** проверьте логику транзакций в приложении; для диагностики временно используйте
`@EnableTestKafka(inflight = false)` — режим Admin API покажет, что видит брокер.

### Причина 4: SUT ещё не стартовал

Приложение поднимает Kafka-контейнеры асинхронно, и на момент проверки группы SUT ещё нет на брокере
(или она перестраивается). Если группы перечислены в
[`expected-groups`](Configuration.md#ожидание-готовности-sut-expected-groups), фреймворк ждёт их
появления до `startup-stabilization-timeout-seconds`, а затем падает с сообщением
`Kafka startup stabilization timeout ...` или
`Kafka wait completion timeout. expected consumer groups are not ready: ...`.

**Решение:** проверьте, что контейнеры SUT действительно запускаются, и при необходимости увеличьте
`startup-stabilization-timeout-seconds`. Убедитесь, что в `expected-groups` перечислены только
подписочные группы: группы с ручным `assign` на брокере видны как `EMPTY`, и ожидание по ним не
завершится.

Ошибка: `No adapter found from [...] to [KafkaRecordSerializer]`
----------------------------------------------------------------

### Симптомы

При старте кейса падает:

```text
No adapter found from [java.util.ArrayList] to [...KafkaRecordSerializer] under configuration
[RecordProperties]. Supported source types: [Serializer, TestSerdeSerializer]
```

### Причина

В `serializer` указан `type`, который не умеет сериализовать сообщения (в примере — произвольный
класс `java.util.ArrayList`), и фреймворк не знает, как его применить.

### Решение

Используйте поддерживаемый формат (`string`, `json`, `xml`, `bytes`, `yaml`, `spring-json`,
`spring-xml`), нативный класс Kafka (`org.apache.kafka.common.serialization.*`) или свой
сериализатор записи (см. [Расширяемость](Extensibility.md)). Список источников, которые принимает
фреймворк, приведён в тексте ошибки.

Ошибка при старте: `Connection [...] must have bootstrapServers configured`
---------------------------------------------------------------------------

### Симптомы

Контекст теста не поднимается:

```text
Connection [kafka1] must have bootstrapServers configured
```

### Причина

У подключения не заполнен `bootstrap-servers`. Адрес обязателен — без него фреймворк не создаст
клиентов.

### Решение

Добавьте адрес брокера в конфигурацию подключения:

```yaml
integration:
  testing:
    kafka:
      connections:
        kafka1:
          bootstrapServers: ${embedded.kafka.brokerList}
```

Ошибка: `Kafka context is being built but no instrumentation plugins are active`
--------------------------------------------------------------------------------

### Симптомы

При запуске теста контекст падает с упоминанием `@Order on JunitExtension` и `@IntegrationTesting`.

### Причина

Kafka-контекст собран раньше, чем JUnit-расширение фреймворка успело активировать инструментацию.
Обычно это признак того, что тест запущен без `@EnableTestKafka` (или с несовместимым порядком
расширений).

### Решение

Запускайте тест через `@EnableTestKafka`; не переопределяйте порядок JUnit-расширений вручную. Если
инструментация клиентов невозможна, используйте `@EnableTestKafka(inflight = false)` — это более
медленный режим через Admin API.

Ошибка при старте: `Invalid serializer config at connection[...]`
----------------------------------------------------------------

### Симптомы

Контекст не поднимается, в сообщении есть путь до настройки:

```text
Invalid serializer config at connection[kafka1].topics[order-in]: Conflicting serde config: ...
```

### Причина

Недопустимая комбинация настроек serde: например, `bean-ref` вместе с `key`/`value`/`headers` или
`type: json` вместе с `value`.

### Решение

Приведите конфигурацию к одной из допустимых схем: «запись целиком» или «по частям». Полная таблица —
в [Конфигурации](Configuration.md). Текст ошибки подсказывает, что именно конфликтует.

Метод не вызывается, хотя указан в тесте
----------------------------------------

### Симптомы

В кейсе указаны и `<inboundMessage>`, и `<bean>`/`<method>`. Тест проходит, но метод приложения не
выполняется: например, не появляется ожидаемое `<outboundMessage>` или изменения в состоянии.

### Причина

Кейс запускается либо сообщением, либо вызовом метода — это взаимоисключающие способы. Если в тесте
есть `<inboundMessage>`, фреймворк выполняет только отправку сообщения, а `<bean>`/`<method>`
игнорирует.

### Решение

Разнесите действия по разным кейсам или `Part`'ам: отдельный тест с `<inboundMessage>` для сообщения
из Kafka и отдельный тест с `<bean>`/`<method>` для вызова метода. Подробнее —
[Записи Kafka](Records-and-Headers.md).

Сообщение не появляется в проверках
-----------------------------------

### Симптомы

`<outboundMessage>` не находит ожидаемое сообщение, хотя приложение его отправило.

### Причина 1: топик исключён из захвата

У топика или подключения стоит `ignore: true`.

**Решение:** уберите флаг для топика, который нужно проверять. Помните, что на отправку сообщений
из теста `ignore` не влияет — только на захват.

### Причина 2: сработал `ignore-inbound`

Сообщение отправил сам тест, а не приложение, и оно скрыто настройкой `ignore-inbound: true`
(поведение по умолчанию).

**Решение:** если нужно видеть весь поток, включая отправленное тестом, заведите
подключение-«монитор» с `ignoreInbound: false`.

### Причина 3: выражение топика не совпало

Ключ в `topics` — это регулярное выражение с полным совпадением. Например, `order-.*` совпадёт с
`order-created`, но `order` — нет.

**Решение:** проверьте выражение; помните, что первое совпадение выигрывает, а результат кэшируется.
Не делайте выражения перекрывающимися.

Данные не десериализуются
-------------------------

### Симптомы

В Diff видно «сырую» запись (UTF-8) и `<exception>` с ошибкой Jackson.

### Причина

`deserializer` топика не соответствует формату данных, которые отправляет приложение, или не указан
`target-class`.

### Решение

Настройте `deserializer` под реальный формат (см. [Serde](Serde.md)). Если «плохие» данные — часть
проверяемого сценария, опишите ошибку через `<exception>` (см.
[Записи Kafka](Records-and-Headers.md)).

Тесты не запускаются без Docker
-------------------------------

### Симптомы

При запуске тестов Kafka возникают ошибки Testcontainers или контекст не поднимается из-за
недоступного брокера.

### Причина

Embedded Kafka поднимается через Testcontainers и требует запущенного Docker; адрес брокера
подставляется из `${embedded.kafka.brokerList}`.

### Решение

Запустите Docker и убедитесь, что в конфигурации нет «зашитого» адреса брокера вместо
`${embedded.kafka.brokerList}`.
