Конфигурация модуля Redis: Справочник параметров
=================================================

[English version](../../en/redis/Configuration.md)

Все параметры тестирования Redis описываются в стандартных конфигурационных файлах Spring Boot (таких
как `application.yml` или `application-test.yml`) под префиксом `integration.testing.redis`.

Настройки позволяют декларативно связывать файлы конфигурации со Spring-бинами соединений в вашем
проекте, автоматически наследовать общие параметры и бесконфликтно разрешать правила сериализации.

Связь конфигурации со Spring-бинами подключений (Connections)
-------------------------------------------------------------

Ключевым разделом является блок `connections`. Имена подразделов в этой секции должны в точности
совпадать с именами бинов `RedisConnectionFactory`, которые объявлены в Java-коде вашего приложения.

Если в вашем проекте объявлены две фабрики соединений (например, одна для Jedis, другая для Redisson):

```java

@Configuration
public class MyRedisAppConfig {

    @Bean
    public RedisConnectionFactory redissonConnectionFactory() {
        return new RedissonConnectionFactory(...)
    }

    @Bean
    public RedisConnectionFactory jedisConnectionFactory() {
        return new JedisConnectionFactory(...);
    }

```

То в файле `application-test.yml` вы описываете подключение, используя эти же имена бинов в качестве
ключей в блоке `connections`:

```yaml
integration:
  testing:
    redis:
      connections:
        # Имя ключа совпадает с именем бина @Bean для Redisson
        redissonConnectionFactory:
          host: "localhost"
          port: 6379

        # Имя ключа совпадает с именем бина @Bean для Jedis
        jedisConnectionFactory:
          host: "localhost"
          port: 6380
```

Если ваше приложение использует стандартную автоконфигурацию Spring Boot и у вас только одна база
данных, то имя бина по умолчанию — `redisConnectionFactory`.

Пошаговая схема наследования и глубокого слияния (Deep Merge)
-------------------------------------------------------------

Параметры не просто копируются, а проходят через трехуровневый процесс глубокого объединения сверху вниз:

```
[ Уровень 1: Глобальные настройки ] (задаются прямо в `integration.testing.redis.*`)
                 │
                 ▼
  [ Уровень 2: Настройки Подключения ] (переопределяют глобальные для конкретного бина)
                 │
                 ▼
  [ Уровень 3: Настройки Схемы Ключа ] (задают правила для конкретной маски/префикса ключа)
```

### Правила слияния параметров

**Простые значения (String, Integer, Boolean, Long):**

* Если у дочернего объекта (например, конкретной схемы) значение поля равно `null`, оно заменяется
  унаследованным значением родителя.
* Если у дочернего объекта поле заполнено, оно сохраняется, а значение родителя игнорируется.

**Списки и множества (`Set<String>` excludedFields):**

* Выполняется операция объединения (Union). Все уникальные элементы из родительских списков добавляются
  к дочернему.
* Пример: Если на глобальном Уровне 1 вы указали исключить `createdAt`, на Уровне подключения 2 вы
  добавили `updatedAt`, а на Уровне схемы конкретного ключа 3 вы добавили `hits` — фреймворк
  автоматически исключит все три поля: `createdAt`, `updatedAt` и `hits`.

**Взаимоисключающие поля (`bean-ref` и `type`):**

* Внутри базы записи, каждого компонента схемы и в кодеке ключей (`keyCodec`) `beanRef` и `type` —
  два взаимоисключающих способа задать источник: можно указать только один.
* Если в дочерней конфигурации заполнено хотя бы одно из этих полей, второе от родителя не
  наследуется. Так исключается конфликт, когда дочерний компонент задаёт `bean-ref`, а от родителя
  «приходит» ещё и `type`.

Исчерпывающий справочник всех параметров
----------------------------------------

### Параметры Глобального уровня (`integration.testing.redis.*`)

Эти настройки применяются ко всем подключениям по умолчанию.

| Параметр               | Тип                       | Описание                                                                     | Значение по умолчанию        |
|------------------------|---------------------------|------------------------------------------------------------------------------|------------------------------|
| `host`                 | String                    | Хост для подключения к Redis (репликатор подключается к нему)                | `${embedded.redis.host}`     |
| `port`                 | Integer                   | Порт для подключения к Redis                                                 | `${embedded.redis.port}`     |
| `user`                 | String                    | Имя пользователя для авторизации в Redis (root приравнивается к null)        | `${embedded.redis.user}`     |
| `password`             | String                    | Пароль для авторизации                                                       | `${embedded.redis.password}` |
| `multipleDatabases`    | Boolean                   | Режим поддержки разделения ключей по индексам баз данных (`SELECT`)          | `false`                      |
| `syncBarrierTimeoutMs` | Long                      | Максимальное время ожидания барьера синхронизации репликации в миллисекундах | `5000`                       |
| `keyCodec`             | Serde-конфиг              | Конфигурация глобального кодека для ключей                                   | `string`                     |
| `defaultSchema`        | Schema                    | Глобальная схема сериализации по умолчанию                                   | все компоненты — `string`    |
| `excludedFields`       | Set\<String\>             | Глобальный список исключаемых полей для сравнения в DTO/мапах                | Пусто                        |
| `connections`          | Map\<String, Connection\> | Карта подключений Redis, ключи — имена бинов `RedisConnectionFactory`        | Пусто                        |

### Структура кодека ключей (`keyCodec`)

Кодек ключей — это одиночный (однослотовый) источник: core-провайдер (`string`, `json`, ...),
Spring Data `RedisSerializer` или Redisson `Codec`/`RedissonClient`. Общие поля
и правила выбора источника задаёт конфиг ядра serde
(`io.github.dimkich.integration.testing.serde.StandardSerdeProperties`).

| Параметр         | Тип    | Описание                                                                    | Эксклюзивность |
|------------------|--------|-----------------------------------------------------------------------------|----------------|
| `type`           | String | Имя core-провайдера (`string`, `json`, ...) или полное имя класса источника | Группа `"ref"` |
| `beanRef`        | String | Имя Spring-бина источника                                                   | Группа `"ref"` |
| `binaryEnvelope` | String | Шаблон бинарной упаковки ключей                                             | —              |

### Структура схемы (`defaultSchema`, `schemas.*`)

Схема описывается компонентами — `value`, `hash-key`, `hash-value`, каждый со своим однослотовым
источником (core-провайдер, Spring Data `RedisSerializer` или Redisson `Codec`/`RedissonClient`).
Незаданные компоненты наследуются от родительской схемы слиянием параметров; в компоненте можно
задать только `binary-envelope` — источник придёт из родительской схемы.

| Параметр            | Тип           | Описание                                                                                              | Эксклюзивность |
|---------------------|---------------|-------------------------------------------------------------------------------------------------------|----------------|
| `type`              | String        | Имя core-провайдера (`string`, `json`, ...) или полное имя класса источника — база для всех компонент | Группа `"ref"` |
| `bean-ref`          | String        | Имя Spring-бина источника — база для всех компонент                                                   | Группа `"ref"` |
| `target-class`      | String        | Класс значения для провайдеров `json`/`xml`/`yaml` — база для всех компонент                          | —              |
| `object-mapper-ref` | String        | Имя бина `ObjectMapper` для провайдеров `json`/`xml`/`yaml` — база для всех компонент                 | —              |
| `value`             | Serde-конфиг  | Кодек простых значений и элементов списков/множеств/потоков                                           | —              |
| `hash-key`          | Serde-конфиг  | Кодек ключей хэша (Hash Fields)                                                                       | —              |
| `hash-value`        | Serde-конфиг  | Кодек значений хэша (Hash Values)                                                                     | —              |
| `ignore`            | Boolean       | `true` — полностью игнорировать подходящие под эту схему ключи (скрыть их из проверок)                | —              |
| `excludedFields`    | Set\<String\> | Список полей значений этих ключей, которые будут исключены из сравнения                               | —              |

### База записи

Поля `type`, `bean-ref`, `target-class`, `object-mapper-ref` можно задать прямо на уровне схемы —
это база для всех компонент: при загрузке конфигурации они вливаются в `value`, `hash-key` и
`hash-value`, а заданное в компоненте значение перекрывает базу. Если база не задаёт источник,
компоненты используют `string`. `binary-envelope` в базе не поддерживается: конверт задаётся
у каждой компоненты отдельно.

```yaml
defaultSchema:
  type: json
  value:
    type: bytes   # компонент перекрывает базу
```

При наследовании база проходит по той же цепочке (глобальная схема → схема подключения → схема
префикса), а `bean-ref` и `type` остаются взаимоисключающими: источник дочерней схемы блокирует
наследование источника родителя.

Каждый компонент — обычный конфиг ядра serde
(`io.github.dimkich.integration.testing.serde.StandardSerdeProperties`):

| Параметр          | Тип    | Описание                                                                    | Эксклюзивность |
|-------------------|--------|-----------------------------------------------------------------------------|----------------|
| `type`            | String | Имя core-провайдера (`string`, `json`, ...) или полное имя класса источника | Группа `"ref"` |
| `beanRef`         | String | Имя Spring-бина источника                                                   | Группа `"ref"` |
| `targetClass`     | String | Класс значения для провайдеров `json`/`xml`/`yaml`                          | —              |
| `objectMapperRef` | String | Имя бина `ObjectMapper` для провайдеров `json`/`xml`/`yaml`                 | —              |
| `binaryEnvelope`  | String | Шаблон бинарной упаковки для этого компонента                               | —              |

`target-class` и `object-mapper-ref` можно задавать и в базе записи, и у компоненты (компонента
перекрывает); `binary-envelope` относится только к компонентам.

Пример: источник и конверт у каждого компонента свои:

```yaml
schemas:
  "redisson.value:":
    value:
      bean-ref: testValueSerializer
      binary-envelope: "{FIX(8, 0)}{LEN(LONG, LE)}{CONTENT}"
    hash-key:
      type: org.springframework.data.redis.serializer.JdkSerializationRedisSerializer
    hash-value:
      type: org.springframework.data.redis.serializer.JdkSerializationRedisSerializer
```

Формат бинарного конверта описывается шаблоном из сегментов — см.
[Бинарные упаковки](../serde/Binary-Envelopes.md).

Если источник — Redisson `Codec` (в том числе через `RedissonClient`), ядро передаёт компоненту
роль слота: `hash-key` кодируется парой `MapKeyEncoder`/`MapKeyDecoder`, `hash-value` —
`MapValueEncoder`/`MapValueDecoder`, `value` — `ValueEncoder`/`ValueDecoder`. Один и тот же бин
можно указывать во всех трёх компонентах — см.
[Слоты Redisson-кодека](Extensibility.md#слоты-redisson-кодека).

### Наследование компонентов схемы

Схема может задавать только часть компонентов: незаданные наследуются от родительской схемы
слиянием параметров. Иерархия: глобальный `defaultSchema` → `defaultSchema` подключения →
`schemas.<префикс>`. По умолчанию все компоненты — core-провайдер `string`:

```yaml
integration:
  testing:
    redis:
      connections:
        redissonConnectionFactory:
          schemas:
            "user:":
              value:
                type: json        # значения — JSON, hash-key/hash-value — из defaultSchema
```

База записи и компоненты наследуются независимо друг от друга, а внутри базы и компонента
`bean-ref` и `type` — эксклюзивные альтернативы: если дочерняя база или компонент задали свой
источник, источник родителя не подмешивается. `binary-envelope` — обычное поле компоненты: его
можно задать и без источника, тогда конверт накладывается на унаследованный источник.
`excludedFields` объединяются.

### Параметры уровня Подключения (`connections.<ConnectionFactoryName>.*`)

Описывают настройки для конкретной фабрики `RedisConnectionFactory`. Вы можете переопределить здесь
любые параметры Глобального уровня:

| Параметр            | Тип                                                               | Описание                                                                                 | Наследование                                                                         |
|---------------------|-------------------------------------------------------------------|------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| `host`              | String                                                            | Хост для подключения к Redis (репликатор подключается к нему)                            | Переопределяет глобальный `host`                                                     |
| `port`              | Integer                                                           | Порт для подключения к Redis                                                             | Переопределяет глобальный `port`                                                     |
| `user`              | String                                                            | Имя пользователя для авторизации в Redis (root приравнивается к null)                    | Переопределяет глобальный `user`                                                     |
| `password`          | String                                                            | Пароль для авторизации                                                                   | Переопределяет глобальный `password`                                                 |
| `multipleDatabases` | Boolean                                                           | Режим поддержки разделения ключей по индексам баз данных (`SELECT`)                      | Переопределяет глобальный `multipleDatabases`                                        |
| `keyCodec`          | Serde-конфиг                                                      | Конфигурация кодека для ключей этого подключения                                         | Наследует глобальный `keyCodec`; поля переопределяются                               |
| `defaultSchema`     | [`Schema`](#структура-схемы-defaultschema-schemas)                | Схема сериализации по умолчанию для этой фабрики                                         | Наследует глобальный `defaultSchema`; компоненты можно переопределять по отдельности |
| `excludedFields`    | Set\<String\>                                                     | Список исключаемых полей для сравнения в DTO/мапах                                       | Объединяется (Union) с глобальным списком                                            |
| `schemas`           | Map\<String, [`Schema`](#структура-схемы-defaultschema-schemas)\> | Карта индивидуальных схем для групп ключей (Уровень 3). Ключами выступают префиксы масок | Не наследуется (определяется только на уровне подключения)                           |

Разрешение паттернов ключей (Longest-Prefix Match)
---------------------------------------------------

При получении любого ключа из Redis фреймворк должен определить, какую схему использовать. Правило
простое: побеждает самая точная (самая длинная) настройка.

1. Ключ переводится в строковое представление с помощью кодека ключей.
2. Фреймворк ищет наиболее длинный совпадающий префикс среди ключей секции `schemas`: чем точнее
   описан ключ, тем выше у него приоритет.
3. Если совпадение найдено, применяется конфигурация этой схемы.
4. Если совпадение не найдено, применяется дефолтная схема подключения (`defaultSchema`).

### Пример работы поиска

Предположим, у нас настроена следующая конфигурация схем:

```yaml
schemas:
  "redisson.TestRedisDto": # Схема А
    value:
      bean-ref: testValueSerializer
  "redisson.TestRedisDto.backup": # Схема Б
    ignore: true
```

| Ключ                               | Наиболее длинный префикс       | Результат                               |
|------------------------------------|--------------------------------|-----------------------------------------|
| `redisson.TestRedisDto:123`        | `redisson.TestRedisDto`        | Применяется Схема А                     |
| `redisson.TestRedisDto.backup:999` | `redisson.TestRedisDto.backup` | Применяется Схема Б (ключ игнорируется) |
| `redisson.otherKey`                | Совпадений нет                 | Применяется `defaultSchema`             |

### Каналы Pub/Sub

Каналы Pub/Sub разрешаются по тем же правилам: имя канала матчится по тем же префиксам
`schemas` с тем же фолбэком на `defaultSchema`, а кодек `value` подходящей схемы используется
для (де)сериализации полезной нагрузки. Само имя канала кодируется и декодируется кодеком
`keyCodec` подключения, как и имена ключей. Так захватываются и отправляются push-сообщения; подробности —
в [Push-Messages.md](Push-Messages.md).

Репликация ожидается через подсистему wait-completion: после инициализации (чтобы снапшоты и
диффы хранилищ читались из догнанного зеркала) и после действия теста (чтобы push-сообщения и
изменения были захвачены до проверок). Для этого нужно
`integration.testing.wait.completion.enabled=true`; в `redis.properties` оно уже задано, так что
дополнительные свойства в тестах не требуются. При явном `false` модуль не ожидает репликацию.

### Экранирование спецсимволов в YAML

Если ваши ключи содержат точки, квадратные скобки или другие спецсимволы, оборачивайте префиксы
в кавычки и квадратные скобки, чтобы YAML-парсер распознал их корректно:

```yaml
schemas:
  "[redisson.bit]": # Обязательно в кавычках и скобках при наличии точек
    value:
      type: bytes
```

Игнорирование технического «шума» (`ignore: true`)
---------------------------------------------------

Часто во время теста фоновые процессы приложения пишут в Redis техническую информацию (сервисные
логи, сессии фоновых задач, блокировки замков Lock). Эти изменения засоряют блок сравнения данных
`dataStorageDiff` и приводят к падению тестов из-за непредсказуемого поведения.

Вы можете сказать фреймворку полностью игнорировать такие ключи с помощью параметра `ignore: true`:

```yaml
schemas:
  # Полностью игнорируем любые ключи блокировок Redisson Lock
  "redisson_lock:":
    ignore: true
```

Игнорируемые ключи будут автоматически отфильтрованы и не попадут в отчёты сравнения и блоки
`dataStorageDiff`.

Полный практический пример конфигурационного файла (application-test.yml)
-------------------------------------------------------------------------

Ниже представлен пример настройки тестовой среды с двумя Redis-подключениями и иерархическим
переопределением сериализации:

```yaml
integration:
  testing:
    redis:
      # --- УРОВЕНЬ 1: Глобальные настройки ---
      host: ${embedded.redis.host}
      port: ${embedded.redis.port}
      password: ${embedded.redis.password}
      syncBarrierTimeoutMs: 10000   # Ждём подтверждения транзакций до 10 секунд

      # Исключаем технические даты для всех DTO во всех базах по умолчанию
      excludedFields:
        - "createdAt"
        - "updatedAt"

      # По умолчанию все компоненты — core-провайдер `string` (это и есть дефолт)
      defaultSchema:
        value:
          type: string
        hash-key:
          type: string
        hash-value:
          type: string

      connections:
        # --- УРОВЕНЬ 2: Подключение "redissonConnectionFactory" ---
        redissonConnectionFactory:
          defaultSchema:
            # Переопределяем компоненты подключения (например, на Jdk-сериализацию)
            value:
              type: "org.springframework.data.redis.serializer.JdkSerializationRedisSerializer"
            hash-key:
              type: "org.springframework.data.redis.serializer.JdkSerializationRedisSerializer"
            hash-value:
              type: "org.springframework.data.redis.serializer.JdkSerializationRedisSerializer"
          schemas:
            # --- УРОВЕНЬ 3: Схемы этого подключения ---
            "[redisson.TestRedisDto]":
              value:
                bean-ref: "testValueSerializer"
              excludedFields:
                - "metrics.hits"   # Дополнительно исключаем счётчик кликов внутри DTO
            "[redisson.bit]":
              value:
                type: bytes
              hash-key:
                type: bytes
              hash-value:
                type: bytes
            "[redisson.envelope]":
              # Компоненты: источник и формат — у каждой части свои
              value:
                bean-ref: "testValueSerializer"
                binary-envelope: "{VER(1)}{LEN(INT, BE)}{CONTENT}"
              hash-key:
                type: "org.springframework.data.redis.serializer.JdkSerializationRedisSerializer"
              hash-value:
                type: "org.springframework.data.redis.serializer.JdkSerializationRedisSerializer"
            "redisson_lock:":
              ignore: true

        # --- УРОВЕНЬ 2: Подключение "jedisConnectionFactory" ---
        jedisConnectionFactory:
          multipleDatabases: true
          defaultSchema:
            excludedFields:
              - "version"           # Дополнительно исключаем версию для этого подключения
          schemas:
            redisson:
              ignore: true
```
