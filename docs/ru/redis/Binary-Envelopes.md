Работа с бинарными упаковками (Binary Envelopes)
=================================================

[English version](../../en/redis/Binary-Envelopes.md)

В реальных проектах данные в Redis часто хранятся не в чистом виде (например, JSON или строка),
а упаковываются во внутренние бинарные конверты (envelopes) клиентских библиотек или кастомных
протоколов.

Типичные примеры:

* Redisson автоматически дописывает к вашему значению служебный заголовок (кодек-маркер, таймстампы
  или длину).
* Собственные протоколы могут требовать наличия в начале каждого пакета сигнатуры (magic bytes),
  версии протокола, длины полезной нагрузки, а в конце — контрольной суммы (CRC32).

Фреймворк решает эту задачу декларативно с помощью парсера шаблонов. Вы можете описать структуру
бинарного конверта прямо в конфигурации `application-test.yml` с помощью простого текстового шаблона.

Структура бинарного конверта
----------------------------

Бинарный конверт состоит из упорядоченного списка сегментов. Вся цепочка делится на три логические
части относительно полезной нагрузки:

```
┌─────────────────────────────────┬───────────┬─────────────────────────────────┐
│         Заголовок (Header)      │  Полезная │          Подвал (Footer)        │
│                                 │  нагрузка │                                 │
├──────────────┬──────────┬───────┼───────────┼─────────┬───────────┬───────────┤
│ {VER(byte)}  │  {FIX}   │ {LEN} │ {CONTENT} │  {TS}   │  {FIX}    │  {CRC32}  │
└──────────────┴──────────┴───────┴───────────┴─────────┴───────────┴───────────┘
```

* **Заголовок (Header):** Все сегменты, объявленные до тега `{CONTENT}`. При чтении они обрабатываются
  первыми.
* **Полезная нагрузка (`{CONTENT}`):** Ваше основное сериализованное значение (например, JSON вашего
  DTO). В шаблоне должен присутствовать ровно один такой сегмент.
* **Подвал (Footer):** Все сегменты, объявленные после тега `{CONTENT}`.

Синтаксис описания шаблонов
---------------------------

Шаблон представляет собой строку, содержащую шестнадцатеричные символы и управляющие теги
в фигурных скобках `{}`.

### Простые байты (статические шестнадцатеричные символы)

Любые символы вне фигурных скобок трактуются как шестнадцатеричные байты. Они записывают
фиксированные маркеры.

* **Пример:** `524453` запишет в поток 3 байта: `0x52 0x44 0x53` (ASCII-строка "RDS"). При чтении
  эти байты просто пропускаются.

### Порядок байт и типы данных для параметров

При настройке параметров числовых тегов используются стандартные типы данных и порядки байт.

**Типы данных:**

| Тип               | Размер  | Описание                 |
|-------------------|---------|--------------------------|
| `LONG`            | 8 байт  | 64-битное целое число    |
| `INT` / `INTEGER` | 4 байта | 32-битное целое число    |
| `SHORT`           | 2 байта | 16-битное целое число    |
| `BYTE`            | 1 байт  | 8-битное целое число     |
| `DOUBLE`          | 8 байт  | Число с плавающей точкой |
| `FLOAT`           | 4 байта | Число с плавающей точкой |

**Порядок байт:**

| Порядок                            | Описание                                                 |
|------------------------------------|----------------------------------------------------------|
| `BE` / `BIG_ENDIAN` (по умолчанию) | Старший байт первый (сетевой порядок байт)               |
| `LE` / `LITTLE_ENDIAN`             | Младший байт первый (стандартный для архитектур x86/x64) |

Справочник встроенных тегов
---------------------------

### Полезная нагрузка: `{CONTENT}`

Обозначает местоположение основного значения.

* Параметры: Нет.

### Префикс длины: `{LEN}`

Записывает длину полезной нагрузки в байтах. При чтении указывает сегменту `{CONTENT}`, сколько байт
необходимо прочитать.

* Параметры:
    * `type` (опционально, по умолчанию `INT`): Тип данных поля длины.
    * `order` (опционально, по умолчанию `BE`): Порядок байт.
* Примеры:
    * `{LEN}` — 4 байта, Big-Endian.
    * `{LEN(SHORT, LE)}` — 2 байта, Little-Endian.

### Версия протокола: `{VER}`

Записывает один фиксированный байт версии и проверяет его при чтении.

* Параметры:
    * `version` (обязательный): Байт версии в десятичном или шестнадцатеричном формате.
* Примеры:
    * `{VER(1)}` — ожидает и записывает байт `0x01`.
    * `{VER(0x05)}` — ожидает и записывает байт `0x05`. При несовпадении во время чтения выбрасывает
      ошибку.

### Временная метка: `{TS}`

Записывает текущее время выполнения теста в миллисекундах (Unix Timestamp). При чтении эти байты
просто пропускаются.

* Параметры:
    * `type` (обязательный): Тип данных для таймстампа (обычно `LONG`).
    * `order` (обязательный): Порядок байт.
* Пример: `{TS(LONG, BE)}` — 8 байт таймстампа.

### Контрольная сумма: `{CRC32}`

Вычисляет контрольную сумму CRC32 для всех байтов пакета, записанных до этого сегмента. Занимает
ровно 4 байта.

* Параметры:
    * `order` (опционально, по умолчанию `BE`): Порядок байт для записи контрольной суммы.
* Примеры:
    * `{CRC32}` — 4 байта CRC32, Big-Endian.
    * `{CRC32(LE)}` — 4 байта, Little-Endian.

### Заполняющие байты (Филлеры): `{FIX}`

Записывает фиксированное количество байт-заполнителей. При чтении просто пропускает это расстояние.

* Параметры:
    * `size` (обязательный): Количество байт.
    * `value` (опционально, по умолчанию `0`): Значение байта в десятичном или шестнадцатеричном
      формате.
* Примеры:
    * `{FIX(8, 0)}` — 8 байт со значением `0x00`.
    * `{FIX(2, 0xFF)}` — 2 байта со значением `0xFF`.

### Текстовые строки: `{STR}`

Позволяет встраивать текстовые маркеры в кодировке UTF-8.

* **Вариант 1 (Фиксированный текст):** `{STR(текст)}` — записывает байты переданной строки. При
  чтении пропускает их.
    * Пример: `{STR(PING)}` запишет 4 байта: `PING` в ASCII.
* **Вариант 2 (Строка с длиной):** `{STR(текст, type, order)}` — записывает сначала длину строки,
  а затем саму строку.
    * Пример: `{STR("Hello", INT, BE)}` запишет 4 байта длины строки (5) и далее 5 байт текста.
* **Экранирование кавычек:** Если текст содержит запятые, скобки или кавычки, его необходимо обернуть
  в одинарные `'` или двойные `"` кавычки. Внутри двойных кавычек внутренние кавычки экранируются: `\"`.
    * Примеры: `{STR('Hello, World')}`, `{STR("He said \"Hi\"")}`.

Создание кастомных бинарных тегов
---------------------------------

Если вашему проекту требуются специфические алгоритмы (например, наложение XOR-маски на байты или
кастомное шифрование), вы можете расширить парсер собственными тегами. Для этого реализуйте
`BinarySegment` и `BinarySegmentProvider` и зарегистрируйте провайдер как `@Component`.

Подробный пример создания тега `{XORMASK(mask)}` описан в руководстве
[Extensibility.md](Extensibility.md#собственные-теги-бинарного-формата-binarysegmentprovider-binarysegment).

Примеры практических конфигураций
---------------------------------

### Пример 1: Формат Redisson

По умолчанию многие кодеки Redisson дописывают к сериализованному значению 8 пустых байт-заполнителей
и 8-байтовую длину в формате Little-Endian:

```yaml
integration:
  testing:
    redis:
      connections:
        redissonConnectionFactory:
          defaultSchema:
            bean-ref: "redissonClient"
            # Описываем бинарный формат Redisson
            valueBinaryFormat: "{FIX(8, 0)}{LEN(LONG, LE)}{CONTENT}"
```

### Пример 2: Кастомный сетевой пакет с контрольной суммой

Предположим, ваше приложение общается с Redis по следующему протоколу:

* Сигнатура (magic bytes) — `AA` (1 байт)
* Байт версии — `05` (1 байт)
* Таймстамп создания — `LONG` (8 байт, Big-Endian)
* Длина полезной нагрузки — `SHORT` (2 байта, Big-Endian)
* Полезная нагрузка (`CONTENT`)
* Контрольная сумма CRC32 — 4 байта (Big-Endian) в самом конце.

Настройка в YAML будет выглядеть так:

```yaml
schemas:
  "secure-queue:":
    class-ref: io.github.dimkich.integration.testing.redis.schema.ComposedRedisDataSchema
    valueBinaryFormat: "AA{VER(5)}{TS(LONG, BE)}{LEN(SHORT, BE)}{CONTENT}{CRC32}"
```
