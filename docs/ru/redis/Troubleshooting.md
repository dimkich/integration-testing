Решение проблем и частые ошибки в тестах Redis
===============================================

[English version](../../en/redis/Troubleshooting.md)

При написании интеграционных тестов с Redis вы можете столкнуться с типичными ошибками конфигурации,
несовпадением типов данных или зависанием тестов. В этом руководстве собраны наиболее популярные
проблемы и способы их быстрого решения.

Ошибка: Method not found in bean `<имя_бина>`
----------------------------------------------

### Симптомы

Вы запускаете тест, но он падает на этапе вызова метода Spring-бина со следующим сообщением в логах:

```
java.lang.RuntimeException: Method rPush not found in bean redisStringFacade
```

### Причина 1: Не указан тип для не-строковых аргументов в XML

По умолчанию все теги `<value>` и `<request>` в XML без явного указания атрибута `type` трактуются
фреймворком как строки (`String`). Если ваш метод в Java принимает `Integer`, `Long` или `Boolean`,
рефлексия Java не сможет сопоставить типы.

**Как исправить:** Всегда явно указывайте типы для чисел и флагов:

```xml
<!-- ❌ Неправильно (ищет метод с параметром String) -->
<request>10</request>

        <!-- ✅ Правильно -->
<request type="Integer">10</request>
```

### Причина 2: Неправильный тип для параметров переменной длины (Varargs)

Если вы вызываете метод с переменным числом аргументов (Varargs в Java, например,
`String... values`), передача списка элементов через обычный `ArrayList` вызовет ошибку, так как
Java-рефлексия ожидает строго массив `Object[]`.

**Как исправить:** Оборачивайте список аргументов в тип `Object[]`:

```xml
<!-- Метод: public Long rPush(String key, String... values) -->
<request>my:list:key</request>
        <!-- ✅ Явно оборачиваем переменные аргументы в массив -->
<request type="Object[]">
<item>значение_1</item>
<item>значение_2</item>
</request>
```

Ошибка: No handler for `<Класс_события>`
-----------------------------------------

### Симптомы

При выполнении операции в Redis фоновый репликатор падает с критической ошибкой, которая затем
транслируется в ваш тест:

```
java.lang.UnsupportedOperationException: No handler for com.moilioncircle.redis.replicator.rdb.datatype.KeyStringValueModule
```

### Причина и решение

Фоновый сетевой репликатор встретил во входящем потоке данных событие, для которого в тестовом
окружении нет зарегистрированного обработчика. Чаще всего это происходит при использовании сторонних
модулей Redis (например, вы пишете JSON-документы через модуль RedisJSON, генерирующий события
`KeyStringValueModule`) или при записи сложных системных объектов.

Поскольку репликатор не знает, как разобрать структуру этого события, он не может продолжить работу
и аварийно завершает поток репликации.

**Как исправить:** Для поддержки нового типа событий необходимо реализовать для него соответствующий
обработчик в Java-коде тестов — `RedisSnapshotHandler` (если событие происходит при чтении снимка RDB)
или `RedisStreamHandler` (если событие происходит при чтении живого потока команд). Подробный пример
написания такого обработчика представлен в руководстве `Extensibility.md`.

Ошибка: Зависание теста или Redis Sync Timeout
----------------------------------------------

### Симптомы

Тест запускается, но «зависает» на несколько секунд, после чего падает со следующей ошибкой:

```
java.lang.RuntimeException: Redis Sync Timeout/Error for [redissonConnectionFactory] using PUBLISH
```

### Причина и решение

Блокирующий барьер синхронизации (`RedisSyncBarrier`) отправил в Redis маркерную Pub/Sub команду
`PUBLISH`, но фоновый поток репликации не смог прочитать её из сети за отведённое время (по умолчанию
5 секунд).

**Как исправить:**

1. **Проверьте логи консоли выше ошибки:** Если фоновый поток репликации упал (например, из-за
   неверного пароля или ошибки авторизации), ошибка попадёт в состояние синхронизации и будет
   выброшена с реальным стек-трейсом. Устраните первопричину (например, укажите верный пароль
   в `application-test.yml`).
2. **Проверьте, запущена ли база данных:** Убедитесь, что Docker-контейнер Redis успешно запустился
   и отвечает на запросы.
3. **Увеличьте таймаут ожидания:** Если база данных перегружена или вы запускаете тесты на слабой
   машине (например, в CI/CD), увеличьте таймаут барьера в `application-test.yml`:

```yaml
integration:
  testing:
    redis:
      # Увеличиваем таймаут синхронизации до 15 секунд
      syncBarrierTimeoutMs: 15000
```

Конфликт Pub/Sub каналов
------------------------

### Симптомы

Тесты с Redis проходят в изоляции, но начинают падать с `Redis Sync Timeout`, когда в проекте
появляются новые подписки на Pub/Sub.

### Причина

Фреймворк использует зарезервированный Pub/Sub канал `__integration_testing_sync__` для
рукопожатия барьера синхронизации. Если ваше приложение (или сторонняя библиотека) подписывается
на этот же канал, сообщения барьера могут быть перехвачены и не дойти до репликатора.

### Решение

Убедитесь, что ни в коде приложения, ни в тестовых сценариях нет подписок на канал
`__integration_testing_sync__`. При необходимости переименуйте канал в вашем коде, избегая
префикса `__integration_testing_`.

Проблема: Изменения в базе не отображаются в dataStorageDiff (пустой дифф)
--------------------------------------------------------------------------

### Симптомы

Приложение успешно отработало, записало данные в Redis, но в блоке `dataStorageDiff` фреймворк
показывает, что никаких изменений в базе не произошло (или показывает пустой блок изменений).

### Причина 1: Несовпадение имени подключения в YAML

Вы настроили схемы сериализации для одного имени подключения, а ваше приложение использует другое.

**Как исправить:** Убедитесь, что в блоке `connections` конфигурационного YAML-файла объявлено
подключение с тем же именем, что используется в `<init name="...">` и `<dataStorageDiff>` (подробнее
см. в файле `Configuration.md`). Это логическое имя; оно не обязано совпадать с именем бина
`RedisConnectionFactory` приложения.

### Причина 2: Ключ попал под фильтр игнорирования (`ignore: true`)

Возможно, префикс вашего ключа совпал с одной из масок, для которых в YAML настроено игнорирование.

**Как исправить:** Проверьте секцию `schemas` в `application-test.yml`. Убедитесь, что ваши бизнес-ключи
не попадают под маски технических ключей, которые вы решили скрыть.

### Причина 3: Не включён режим поддержки нескольких баз данных

Ваше приложение выполняет команду `SELECT 1` (пишет в базу с индексом 1), но в настройках подключения
не включён параметр `multipleDatabases`. В этом случае репликатор считает все ключи относящимися
к базе 0 и не находит изменений.

**Как исправить:** Включите поддержку нескольких БД в свойствах подключения:

```yaml
connections:
  redisConnectionFactory:
    multipleDatabases: true   # <-- Включает корректное разделение ключей по базам
```

Проблема: Push-сообщения не попадают в `outboundMessage`
---------------------------------------------------------

### Симптомы

Приложение опубликовало Pub/Sub сообщение (или тест отправил `<inboundMessage>`), но push
не появляется в `<outboundMessage>` — или, наоборот, появляется неожиданный push.

### Причина 1: Канал игнорируется (`ignore: true`)

Префикс схемы, совпадающий с каналом, помечен `ignore: true`, поэтому захват пропускается.
Это штатный способ скрыть технические каналы.

**Как исправить:** Проверьте секцию `schemas` в `application-test.yml` и уберите или сузьте
ignore-префикс для тестируемого канала.

### Причина 2: Push относится к другому подключению

`connection` в проверке — это имя подключения из `integration.testing.redis.connections`, на
котором push был замечен. Если несколько подключений смотрят в один Redis, каждое захватывает
один и тот же push; игнорируемые префиксы скрывают копии, которые вы не проверяете.

**Как исправить:** Указывайте `connection` явно в `<inboundMessage>`/`<outboundMessage>`,
а дублирующиеся захваты помечайте `ignore: true`.

### Причина 3: SUT ещё не обработал входящий push

Приложение обрабатывает push асинхронно. Фреймворк ждёт, пока поток репликации догонит Redis,
но не ждёт сторону SUT.

**Как исправить:** Дожидайтесь реакции SUT явно в тесте (например, методом фасада) перед
проверкой.

### Причина 4: Push отправлен самим тестом

Собственные push-сообщения теста отсеиваются по транспортной идентичности и не попадают
в `<outboundMessage>`. Push-сообщения, опубликованные при запуске приложения, не отсеиваются:
скрывайте технические каналы через `ignore: true`, если их не нужно проверять.

**Как исправить:** Публикуйте push внутри теста и проверяйте только сообщения, созданные SUT.
Подробнее см. [Push-Messages.md](Push-Messages.md).

Ошибка подключения фреймворка к Redis
-------------------------------------

### Симптомы

В логах `RedisClientException`: `Cannot connect to Redis [...]`, `Redis authentication failed`,
`Redis command [...] failed` или `Redis Sync Timeout`.

### Что проверить

1. `host`/`port` заданы явно — в `integration.testing.redis.connections.<имя>` или на
   глобальном уровне `integration.testing.redis.*`. Автоматического fallback-а на
   `embedded.redis.*`/`spring.data.redis.*` нет.
2. Для защищённого Redis заданы `user`/`password`.
3. `timeoutMs` достаточен для вашего окружения (по умолчанию `5000` мс).
4. Если используется TLS — включён `ssl: true` и сертификат сервера доверен JVM.

Фреймворк не использует `RedisConnectionFactory` приложения, поэтому настройки драйвера SUT
(например, Redisson `Config`) на него не влияют — нужны настройки в блоке `connections`.

### Redis 5 и TTL полей хэша

Соединение и все служебные команды работают с Redis 5+. Однако пер-полевой TTL хэша
(`HPEXPIREAT`) появился только в Redis 7.4. Если в тестовых данных у полей `RedisHash` задан
`ttl`/`expireAt`, на Redis 5–7.2 такая запись завершится ошибкой `unknown command`. TTL всего
ключа (`PEXPIREAT`) работает на всех поддерживаемых версиях.
