Расширение diff
================

[English version](../en/Storage-Diff-Extensibility.md)

Эта страница — для случаев, когда стандартных правил `<diff>` не хватает: у вашего типа особый ключ,
значение или тело. Как читать и писать diff, описано в разделе
[Изменения хранилищ](Storage-Diff.md); здесь — API расширения.

## Ключ записи — `addDiffKeyPresenter`

Презентер ключа возвращает тело ключа; форма определяется по этому телу тем же детектором типа,
что и форма значения:

* скалярное тело (`String`, число, enum, `UUID`, `BigDecimal`, тип с `@JsonValue`) — ключ
  пишется одной строкой через сериализатор текущего формата;
* структурное тело (объект, `Map`, `Set`, `Collection`) — ключ пишется объектом: тип, атрибуты и
  тело.

Один метод закрывает оба случая. Для незарегистрированного типа форма выводится автоматически:
скалярный тип пишется строкой, структурный — объектом, спроецированным по правилам Jackson так же,
как значение.

### Текстовый ключ

Если ключ нужно сократить до строки, верните из презентера скаляр:

```java
@Bean
TestSetupModule testSetupModule() {
    return new TestSetupModule()
            .addDiffKeyPresenter(MarketInstrumentKey.class,
                    (key, attributes) -> key.getExchange() + "," + key.getClassCode() + "," + key.getTicker());
}
```

В diff это даёт читаемый ключ:

```xml
<insert key="MOEX,TQCB,SBER">...</insert>
```

Требования к строке: стабильность между запусками, отсутствие переводов строк и управляющих
символов, уникальность в пределах одной map (для записей — в пределах набора записей хранилища).
Фреймворк падает с понятной ошибкой, если два разных ключа одной map дают одинаковую строку. У
текстового ключа нет типа и атрибутов: `type` и `attributes` презентера относятся только к
объектной форме.

### Объектный ключ

Структурный ключ пишется объектом без настройки: незарегистрированный тип проецируется по правилам
Jackson так же, как значение. Ключ — это снимок: тип, атрибуты и тело. Текстовый ключ остаётся
атрибутом `key`, а объектный — дочерним элементом `<key>`; в обычном случае формы не путаются:

```xml
<insert type="MD">
    <key type="MarketInstrumentKey">
        <exchange>MOEX</exchange>
        <classCode>TQCB</classCode>
        <ticker>SBER</ticker>
    </key>
    <value>
        <closePrice type="BigDecimal">259.43</closePrice>
    </value>
</insert>
```

`<value>` содержит тело значения; если значения нет (`delete` или значение только с атрибутами),
`<value>` отсутствует:

```xml
<delete type="MD">
    <key type="MarketInstrumentKey">
        <exchange>MOEX</exchange>
        <classCode>TQCB</classCode>
        <ticker>SBER</ticker>
    </key>
</delete>
```

Элемент без атрибута `key`, тело которого состоит ровно из поля `key` (или `key` и `value`),
структурно совпадает с объектным ключом. Если после `<key>` есть другие поля, они остаются
обычными полями тела.

Что важно знать:

* структурный ключ по умолчанию проецируется по правилам Jackson — так же, как значение; свойства,
  сериализованные как XML-атрибуты, становятся атрибутами ключа;
* `addDiffKeyPresenter(type, presenter)` задаёт своё тело ключа: скалярное тело делает ключ
  строкой, структурное — объектом с кастомной проекцией. Презентеры ключей и значений ищутся
  раздельно: презентер значения для этого типа к ключу автоматически **не** применяется;
* ключ — снимок: его элементы не описывают изменения, поля пишутся именами. Поле с именем, которое
  нельзя использовать как XML-тег, всё равно пишется тегом `<insert key="...">` — это обёртка имени,
  а не операция;
* ключ сравнивается по своему представлению — тип, атрибуты и тело, а не по
  `equals`/`hashCode`/`toString` доменного класса. Поэтому изменяемый ключ и ключ без компактного
  `toString()` работают; два ключа с одинаковым представлением — ошибка;
* объектные ключи записей сортируются детерминированно — по типу, атрибутам и телу;
  `LinkedHashMap`/`LinkedHashSet` сохраняют порядок вставки; `TreeMap`/`TreeSet` сохраняют порядок
  компаратора, даже если их ключи — объектные. Если компаратор опирается на identity hash, порядок
  не будет стабильным: используйте `LinkedHashMap`/`LinkedHashSet` или свой рендерер;
* `MultiValueMap` (например, заголовки Kafka) требует текстовый ключ: повторяющиеся элементы
  пишутся именем поля, поэтому презентер такого ключа должен вернуть скалярное тело;
* если ключ встречается в `<request>`/`<response>` теста, зарегистрируйте его как обычный подтип
  (`addSubTypes`).

## Представление значения — `addDiffPresenter`

Презентер описывает значение методом `present`: он добавляет метаданные в
`DiffAttributes.Builder` и возвращает сырое тело. Билдер проверяет имена и значения, а также задаёт
порядок атрибутов. При необходимости презентер переопределяет `type`, а `TypeNames.typeOf` даёт
имя типа значения. Саму разницу всегда считает фреймворк, поэтому презентер не сравнивает
значения и не выбирает между `insert` и `update`.

```java
public class RedisEntryPresenter implements DiffPresenter<RedisEntry> {

    @Override
    public Object present(RedisEntry entry, DiffAttributes.Builder attributes) {
        attributes.addAttributes(ttl(entry));
        return entry.getData();
    }

    @Override
    public String type(RedisEntry entry, DiffValue body, TypeNames types) {
        return types.typeOf(entry.getData());
    }

    private Map<String, String> ttl(RedisEntry entry) {
        if (entry.getTtl() == null) {
            return Map.of();
        }
        return Map.of("ttl", entry.getTtl().toString());
    }
}
```

Регистрация — обычным методом модуля:

```java
@Bean
TestSetupModule testSetupModule() {
    return new TestSetupModule()
            .addDiffPresenter(RedisEntry.class, new RedisEntryPresenter());
}
```

Что важно знать:

* `present` возвращает тело значения, а атрибуты кладёт в `DiffAttributes.Builder`. Тело —
  обычные данные (map, коллекция, массив или скаляр), и фреймворк диффит их по тем же правилам,
  что и любое другое значение. Объект с полями презентер отдаёт как map — это же делает презентер
  по умолчанию;
* тело — тоже значение: если у его типа есть свой презентер, применяется он, а его атрибуты
  добавляются к атрибутам элемента. Например, `RedisEntryPresenter` отдаёт `RedisZSet`, а
  `RedisZSetPresenter` превращает его в map `member → score`; без этого ZSET потерял бы member'ов.
  Тип элемента при этом задаёт корневой презентер (`type`), а не презентер тела;
* атрибуты — `Map<String, String>`: имя → значение. `addAttribute` валидирует имя и значение сразу;
  одинаковое значение повторно игнорируется, разные значения одного имени — `IllegalStateException`.
  `addAttributes` принимает готовую map: `LinkedHashMap`/`SortedMap` задают порядок, неупорядоченная
  map с 2+ атрибутами сортируется по имени; отсутствующий атрибут просто не добавляется;
* `type` по умолчанию возвращает тип самого значения. Встроенный презентер контейнеров
  (`Map`, `Set`, `Collection`) не пишет тип непустой map, потому что её поля сами описывают
  структуру; пустая map без изменений полей тип сохраняет. Коллекция, множество и массив тип пишут
  всегда: элементы у них безымянные, и без типа не видно, чем именно является контейнер — список
  от массива по телу не отличить. Пользовательский презентер, возвращающий map, тип по умолчанию
  сохраняет — уберите его в `type`, если поля самодостаточны. Переопределяйте метод, только если
  тип элемента должен быть типом тела: например, значение Redis пишется типом payload, а презентер
  базового типа — именем базового типа;
* `type` — часть идентичности значения: если тип до и после различается, элемент пишется как
  `update`, даже когда тело не изменилось. Тип сравнивается по значению, которое вернул
  презентер, а не по Java-классу, поэтому `BaseValue`/`DerivedValue` с одним презентером остаются
  одним типом. Сработавший пользовательский предикат `addEqualsForType` сильнее этой проверки;
* для удалённого значения вызывается только `type`: тело и атрибуты не пишутся;
* тело без данных (`null`) пишется только атрибутами, например `<member score="10.5"/>`;
* имена атрибутов — простые XML-имена без namespace; `key`, `type`, `nil` и `xmlns` зарезервированы
  форматом и не могут быть атрибутами презентера;
* если подходит несколько зарегистрированных презентеров (например, для `Set` и `Collection`),
  выбирается самый специфичный тип: подтип важнее супертипа, порядок регистрации не важен. Для
  одного и того же типа побеждает пользовательский модуль: встроенные регистрации применяются
  первыми;
* разницу тела строит renderer, выбранный по типу тела, поэтому презентер может описать значение,
  не меняя его форму.

Без презентера применяются правила Jackson: поля объекта, `@JsonInclude`,
`@JacksonXmlProperty(isAttribute = true)`. Для `Optional`, `AtomicReference` и
`AtomicMarkableReference` встроенный презентер пишет значение внутри (у markable mark не
участвует, как и в пресете сравнения). `@JsonInclude(NON_DEFAULT)` и кастомные фильтры
презентер по умолчанию не учитывает: для них нужен свой `DiffPresenter`.

## Рендеринг тела — `addDiffRenderer`

Презентер описывает тело значения, а разницу тела строит рендерер. Встроенные рендереры
покрывают `Map`, `Set`, `MultiValueMap`, коллекции, массивы и скаляры; для тела другой формы
нужен свой рендерер:

```java
.addDiffRenderer(Tags.class, new TagsDiffRenderer());
```

Рендерер выбирается по типу финального тела, которое вернул презентер (после всех презентеров
тела), а не по типу значения. Презентер по умолчанию проецирует объект в map, поэтому для
собственного тела нужен презентер, который вернёт это тело. Одного `addDiffRenderer` недостаточно.
Рендерер должен принимать любой подтип зарегистрированного типа: рендерер, типизированный под
`HashMap` и зарегистрированный для `Map.class`, скомпилируется, но упадёт на `LinkedHashMap`.

`DiffRenderer<T>` получает тело до и после теста и возвращает `DiffValue`:

* `before` — тело до теста, которое построил презентер предыдущего значения. Может быть `null`,
  если значения не было, или иметь другой тип, если значение сменило форму. Рендерер сам решает,
  как трактовать тело другой формы: встроенные контейнеры (`Map`, `Set`, `MultiValueMap`)
  сравнивают его с пустым контейнером, поэтому все элементы нового тела пишутся как `insert`;
  скаляр пишется как значение, а последовательность — как снапшот, потому что у неё нет
  идентичности элементов;
* `after` — тело после теста, всегда типа `T`;
* `null` в ответ означает, что тело не изменилось. Это единственный способ сообщить фреймворку, что
  запись без изменений: пустой снапшот (`DiffObjectValue` без полей, `DiffCollectionValue` без
  элементов) — это значение, а не отсутствие изменений, поэтому снапшот никогда не `null`;
* `renderUnchanged` вызывается, когда тело не изменилось, но изменились атрибуты **или тип**
  значения; для `null`-тела метод не вызывается. По умолчанию он возвращает снапшот тела;
  рендерер, который пишет только изменения (как `Map`, `Set` и `MultiValueMap`), переопределяет
  метод и возвращает `null`.

Элементы `Set` сопоставляются по равенству самого множества (`equals`/`hashCode`, а у
`SortedSet` — компаратор), а не по предикатам `addEqualsForType`: множество рассчитано на
значения, которые хорошо сравниваются собственным равенством. Если в множестве лежит
`BigDecimal`, `ZonedDateTime`, `byte[]` или другой тип с нестандартным равенством,
зарегистрируйте свой рендерер для типа множества.

Минимальный рендерер тела-обёртки, который пишет элементы без имён:

```java
public class TagsDiffRenderer implements DiffRenderer<Tags> {

    @Override
    public DiffValue render(Object before, Tags after, ObjectsDifference difference) {
        if (before != null && difference.isEquals(before, after)) {
            return null;
        }
        return new DiffCollectionValue(difference.entries(after.values(), null).toList());
    }
}
```

Для сборки результата используйте `DiffObjectValue` (именованные поля), `DiffCollectionValue`
(безымянные элементы), `DiffScalarValue` и `DiffNullValue`. Методы `ObjectsDifference` —
`insert`, `update`, `deleteElement`, `deleteValue`, `entries`, `forEachField` — строят элементы
и ключи по общим правилам, чтобы рендерер не дублировал сортировку и идентичность. `insert`
пишет снапшот значения, `update` — только изменения (или `null`, если их нет), `deleteElement` —
удаление keyed-элемента без тела, `deleteValue` — удаление значения repeated-поля с телом.
Элементы коллекции или массива получайте через `entries`: массив и упорядоченная коллекция
рендерятся в порядке источника, неупорядоченная — сортируется по готовому элементу.

## Сравнение значений — `addEqualsForType`

Если для типа изменение не является изменением (например, `SecureRandom`), зарегистрируйте
предикат равенства — такая запись не попадёт в diff:

```java
@Bean
TestSetupModule testSetupModule() {
    return new TestSetupModule()
            .addEqualsForType(SecureRandom.class, (first, second) -> true);
}
```

Пользовательский предикат — самый сильный способ сравнения пары значений: он применяется до
рендерера и до проверок типа и наличия тела. Если предикат говорит «равны», запись не попадёт в
diff, даже когда у значения сменился тип или исчезло тело.

Библиотечные пресеты (`BigDecimal`, `ZonedDateTime`, `Temporal`, `Map`, `SecureRandom` и
reference-типы) — это правило равенства. Для plain-скаляров (`BigDecimal` `0.1` и `0.1000`) пресет
подавляет diff; для структурных значений он не скрывает ни атрибуты, ни смену типа. Пользовательский
предикат сильнее: он может скрыть и атрибуты, и смену типа — это осознанный выбор.
