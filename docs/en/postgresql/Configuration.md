PostgreSQL Module Configuration
===============================

[Russian version](../../ru/postgresql/Configuration.md)

The module parameters are defined in standard Spring Boot files (`application.yml`,
`application-test.yml`, etc.) under the `integration.testing.postgresql` prefix.

The framework opens its own JDBC connections using these parameters. It does not need an application
`DataSource` bean, but the application and the test must use the same database; otherwise the diff
will not see application changes.

## Connections

A key in `connections` is a storage name. It is used in XML:

```xml
<init type="SqlStorageSetup" name="dataSource">...</init>
<init type="SqlStorageInit" name="dataSource">...</init>
<dataStorageDiff>
    <dataSource>...</dataSource>
</dataStorageDiff>
```

The name can be arbitrary, for example `dataSource`, `orders`, or `billing`. It does not have to match
an application `DataSource` bean name.

### Global Parameters

Global parameters provide defaults for every connection:

| Parameter     | Type   | Description                       | Default                           |
|---------------|--------|-----------------------------------|-----------------------------------|
| `host`        | String | PostgreSQL host                   | `${embedded.postgresql.host}`     |
| `port`        | String | PostgreSQL port                   | `${embedded.postgresql.port}`     |
| `database`    | String | Database name                     | `${embedded.postgresql.schema}`   |
| `user`        | String | User                              | `${embedded.postgresql.user}`     |
| `password`    | String | Password                          | `${embedded.postgresql.password}` |
| `connections` | Map    | Connections keyed by storage name | empty                             |

The embedded container exposes the database name through the `embedded.postgresql.schema` property,
so the examples reference it for `database`.

### Connection Parameters

Each connection can override the global values:

| Parameter              | Type   | Description                                   | Default  |
|------------------------|--------|-----------------------------------------------|----------|
| `host`                 | String | PostgreSQL host                               | global   |
| `port`                 | String | PostgreSQL port                               | global   |
| `database`             | String | Database name                                 | global   |
| `user`                 | String | User                                          | global   |
| `password`             | String | Password                                      | global   |
| `defaultSchema`        | String | Schema for unqualified names and diff keys   | `public` |
| `batchSize`            | int    | JDBC batch size for DBUnit fixture loading    | `10000`  |
| `sequenceRestartValue` | long   | `RESTART WITH` value for connection sequences | `1`      |
| `columns`              | Map    | Per-column settings                           | empty    |

`defaultSchema` affects how names such as `users` and `orders` are resolved. If the tables live in a
different schema, set `defaultSchema` or use fully qualified `schema.table` names.

The same value controls the table prefix in `<dataStorageDiff>` row keys: tables from
`defaultSchema` use a bare name (`users_1`), while tables from other schemas keep the schema
(`billing.users_1`).

Two connections:

```yaml
integration:
  testing:
    postgresql:
      connections:
        dataSource:
          host: "${embedded.postgresql.host}"
          port: "${embedded.postgresql.port}"
          database: "${embedded.postgresql.schema}"
          user: "${embedded.postgresql.user}"
          password: "${embedded.postgresql.password}"
          defaultSchema: public

        billing:
          host: db.example.test
          port: 5432
          database: billing
          user: test_user
          password: test_password
          defaultSchema: billing
```

### Sequence Restart

When the state is reset around test boundaries, the framework executes the following for sequences
owned by the managed tables:

```sql
ALTER SEQUENCE <sequence> RESTART WITH <sequenceRestartValue>
```

`sequenceRestartValue` defaults to `1`. It is configured per connection and applies to every
sequence of that connection.

There are two common ways to separate fixture IDs from IDs generated by the system under test:

1. Fixtures use IDs starting at `1000`, and the SUT generates IDs starting at `1`. Leave
   `sequenceRestartValue: 1`.
2. Fixtures use IDs starting at `1`, and the SUT must generate IDs starting at `1000`. Set
   `sequenceRestartValue: 1000` (or higher).

```yaml
integration:
  testing:
    postgresql:
      connections:
        dataSource:
          # ...
          sequenceRestartValue: 1000
```

The value must be greater than the maximum explicit ID in the fixtures of every table. Otherwise, the
first SUT `INSERT` can receive an already used ID and fail with a duplicate key error. The setting
also shifts generated IDs and diff keys, so tests that assert absolute IDs must be updated.

If a single table needs a different value, override it with an SQL query in the test after the
automatic sequence reset.

## Diff Shape in XML

The module stores changes in the framework's regular storage. To get the familiar
`MapStringKeyObjectValue` → `EntriesObjectKeyObjectValue` shape with a `change` attribute, add:

```yaml
integration:
  testing:
    storage:
      storages:
        dataSource:
          keyType: [ STRING, OBJECT ]
          valueType: [ OBJECT, OBJECT ]
          changeType: [ false, true ]
```

The levels mean:

* the first element is the root diff, keyed by connection name;
* the second element is a record inside the connection, keyed by a string such as `users_100`.

`changeType` enables `change="added|changed|deleted"`. Add a similar `storages.billing` block for a
second connection.

## Column Settings

The `columns` section overrides serde and excludes data from the diff. The key is
`table.column` or `schema.table.column`.

In YAML, a key containing dots must be quoted and wrapped in brackets:

```yaml
integration:
  testing:
    postgresql:
      connections:
        dataSource:
          columns:
            "[public.users.metadata]":
              type: json
              target-class: com.example.UserMetadata
            "[public.users.technical_note]":
              ignore: true
            "[public.events.payload]":
              type: json
              excludedFields:
                - secret
                - metrics.internal
```

Supported fields:

| Field               | Type          | Purpose                                                    |
|---------------------|---------------|------------------------------------------------------------|
| `type`              | String        | Serde provider name or fully qualified class name          |
| `bean-ref`          | String        | Name of a Spring bean with a ready serializer/deserializer |
| `target-class`      | String        | Value class for `json`/`xml`/`yaml`                        |
| `object-mapper-ref` | String        | `ObjectMapper` bean name for Jackson formats               |
| `binary-envelope`   | String        | Binary envelope template                                   |
| `ignore`            | boolean       | Exclude the whole column from the diff                     |
| `excludedFields`    | Set\<String\> | Nested fields to exclude from the diff                     |

`ignore` excludes the column only from comparison. Audit and revert still use the full value, so such
columns are restored correctly.

`excludedFields` removes the listed nested fields from both states, before and after. Paths are
dot-separated; the rule also applies to elements of JSON arrays.

Primary-key columns cannot be listed in `ignore` or `excludedFields`: they identify a row, so
metadata preparation fails. For a table without a primary key, the whole tuple remains the identity:
`ignore` hides the value from the diff, but changing only that column still appears as a row delete
and insert.

Serde fields are inherited from the shared configuration. See [Types and Serde](Types-and-Serde.md)
and the [Serde overview](../serde/README.md) for details and examples.

## Environment Requirements

The PostgreSQL technical account must be able to:

* connect to the required database;
* create the service journal table, sequence, functions, and triggers in the schema;
* create and drop triggers on the tested tables;
* execute `SET session_replication_role` (normally this is available only to a superuser or a role
  explicitly granted this privilege);
* execute `ALTER SEQUENCE ... RESTART` for sequences owned by the tested tables;
* read from and write to the service journal table.

If the tests use `hstore` columns, the extension must be installed beforehand:

```sql
CREATE EXTENSION IF NOT EXISTS hstore;
```

The module expects the standard `bytea_output = 'hex'`. With `bytea_output = 'escape'`, binary values
may appear as text instead of `byte[]`.

Service tables with the `_it_` prefix are not intended for test data: the module excludes them from
metadata and fixtures. Do not clear or modify them manually.

By default, `@EnableTestPostgreSQL` imports `postgresql.properties` and enables embedded PostgreSQL
from Testcontainers. For an external database, disable the embedded mode through test properties:

```java
@SpringBootTest(properties = {
        "embedded.containers.enabled=false",
        "embedded.postgresql.enabled=false"
})
```

## Complete Example

```yaml
integration:
  testing:
    postgresql:
      connections:
        dataSource:
          host: "${embedded.postgresql.host}"
          port: "${embedded.postgresql.port}"
          database: "${embedded.postgresql.schema}"
          user: "${embedded.postgresql.user}"
          password: "${embedded.postgresql.password}"
          defaultSchema: public
          batchSize: 5000
          columns:
            "[public.documents.content]":
              ignore: true
            "[public.events.payload]":
              type: json
              excludedFields:
                - secret
    storage:
      storages:
        dataSource:
          keyType: [ STRING, OBJECT ]
          valueType: [ OBJECT, OBJECT ]
          changeType: [ false, true ]
```
